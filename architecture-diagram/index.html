Architecture · explained

Fifty million rows, no import, and nothing taken on trust

Mirror the source instead of exporting it, transform where the data already sits, write once, and serve it without importing a second copy. Every figure below was measured on the running system and is re-measured by an acceptance pass that fails loudly; the source is github.com/sulaiman013/fabric-x-duckdb.

How to identify this architecture

An open-mirroring bronze layer fed from a write-ahead log, a single-node DuckDB transformation running on the capacity, and a V-Ordered Delta gold layer served by Direct Lake with no import. If you need one label: a Kimball star schema built by a single-node analytical engine on lakehouse storage, served by Direct Lake, with change-data-capture ingestion. It is deliberately not a Spark architecture, and deliberately not a warehouse one.

  • Mirror, do not export. The source is a PostgreSQL instance on localhost, which Fabric cannot reach and does not support natively. Open mirroring inverts the problem: the publisher writes change files into a landing zone and Fabric's engine applies them, so no inbound connectivity is needed at all.
  • Seed then stream. A 10.5 GB snapshot establishes the baseline; a logical replication slot keeps it live. Neither half is sufficient alone, and the order they are created in matters more than it looks.
  • One node, because the job fits on one. 10.5 GB compressed does not need a cluster. DuckDB on a Fabric Python notebook at 8 vCores bills 4 CU against the Spark starter pool's documented 8, with no shuffle and no cluster start.
  • Spark only where DuckDB cannot go. V-Order is what makes Direct Lake fast and DuckDB cannot write it, so the split falls exactly on that boundary and costs 233 seconds.
  • Serve without importing. Direct Lake reads the same Delta files the notebook wrote. Nothing is imported and nothing refreshes on a schedule, so the model never holds a third copy of the 49.4M rows and never goes stale between refreshes.
  • The report is a program. Each page is one HTML Content visual fed by a DAX measure that ships both a pre-aggregated cube and its own renderer, with no CDN and no external dependency.
  • One surrogate key does three jobs. _mirror_row_id is what makes PostgreSQL emit updates and deletes, what makes 593,209 exact duplicates resolvable when no business column is unique, and what gives the fact table a grain that points at one real source row.
  • Evidence, not assertion. The pipeline writes its own measurements; 36 acceptance checks read them back, chase a live change from PostgreSQL into OneLake by value, and verify that this document still matches the repository.

Step by step, source to report

1
Generate a source worth cleaning50,000,000 rows and 100 columns of deliberately ungoverned banking data: five date formats in one column, money as text, epoch integers beside ISO timestamps, 31 spellings of Malaysia, 1.18% exact duplicates. Entities stay coherent (a customer keeps the same name and date of birth across their rows) so joins and deduplication are real exercises rather than noise.
2
Land it in PostgreSQL, all TEXT, LOGGEDA landing zone that rejects rows is not a landing zone, so every column is TEXT. --logged is not optional: an UNLOGGED table is never captured by logical replication, and the mirror's change feed would silently see nothing. A surrogate key, _mirror_row_id, is added because no subset of the 100 business columns is unique.
3
Create the replication slot, then take the snapshotIn that order. This project did the reverse and paid for it: one row deleted and one inserted fell into the gap, and because the errors had opposite signs the row counts still matched exactly. Finding them needed a distinct-key comparison and a per-bucket hash histogram.
4
Seed the mirror16 zstd parquet files, 10.5 GB, 29 minutes, pushed into the landing zone with azcopy. Metadata is written after the data it describes, or the engine latches on a zero-byte file.
5
Stream the write-ahead logA test_decoding slot is polled every ten seconds. Each change becomes a parquet row carrying __rowMarker__, written as the next 20-digit sequential file; the engine applies it as a Delta merge on the key column. Measured: 151 seconds from an UPDATE in PostgreSQL to the engine's own counter moving.
6
Shortcut the mirror into a lakehouseTables/raw_txn points at the mirrored table, so the transformation reads it in place with delta_scan. This is what stops the transformation staging a copy before it starts.
7
Transform on the capacity, in DuckDBClean and conform 100 text columns, score seven measured rules, resolve 593,209 duplicates, build the star. 770 seconds of work inside an 895 second billed session, on the Python kernel at 8 vCores. The notebook records its own environment, so spark_in_globals: false is the evidence it was not a Spark driver.
8
Pin everything that could driftTimestamps are parsed as naive UTC and the session timezone is pinned, because to_timestamp returns TIMESTAMPTZ and made every derived hour depend on where the code ran. Window tiebreaks order by the surrogate key so they agree with deduplication. Exports cast to instants, because Spark reads a naive column as TIMESTAMP_NTZ and Direct Lake will not serve it.
9
Write V-Ordered Delta with Spark233 seconds, nine tables, 36 files, 2.5 GB. The only Spark in the pipeline, and the only job DuckDB cannot do.
10
Verify on the capacity, not on a laptopRow counts, V-Order table properties and orphan keys are read from the tables themselves and written to verify.json. Zero orphan dimension keys across 49,406,792 fact rows.
11
Serve with Direct Lake9 tables, 8 relationships, 17 measures, authored as TMDL and imported. The first query after a reframe transcodes columns into memory and costs 7 to 11 seconds; every query after that answers in about a second over the full fact.
12
Report in DAX and JavaScriptFour pages, each a single HTML Content visual driven by a measure that ships a 2,508-cell cube and its own renderer inline, using about 4% of the roughly 2.1M character ceiling a measure can hold. Generated, including a native page navigator so it works outside Desktop.
13
Prove all of it, repeatably37 acceptance checks across the repository, ingestion, transformation, the model, the report and the documentation: 36 pass, none fail, one is skipped by a flag. It checks by value: a real UPDATE chased into OneLake, the build compared rule by rule against a baseline, a decision written and read back out of Delta, and this document's own claims checked against the repository.

What each decision buys, and what enforces it

GuaranteeWhat enforces it
The source is never reached intoOpen mirroring inverts the direction: the publisher writes files, Fabric reads them. There is no inbound connection and no credential held by Fabric.
Deletes and updates propagate, not just inserts__rowMarker__ on every change row, and a LOGGED table with REPLICA IDENTITY satisfied, without which UPDATE and DELETE emit nothing.
Two runs produce the same numbersPinned UTC session, naive-UTC epoch parsing, and window tiebreaks ordered by the surrogate key. Asserted rule by rule against a recorded baseline.
No fact row is ever orphanedExplicit Unknown members in every dimension, and an orphan-key check that runs on the capacity and writes its result to an evidence file.
The model cannot drift from the layer it readsDirect Lake over the same Delta files, plus a reconciliation in the acceptance pass: Transactions and Rule Firings must equal the verified counts exactly.
A rule change cannot quietly move a numberSeven rules with recorded fire counts, compared rule by rule against a baseline on every acceptance run, so a change shows up as a diff rather than as a slightly different total.
The documentation cannot quietly go staleThe acceptance pass reads the README: its layout must match the repository file for file, and the numbers it quotes must be the ones the pipeline produced.
Secrets stay out of a public repositoryA scanner over tracked file contents and paths, after a Fabric Git sync published an account identifier as a filename.

The arguments worth having

Why not Spark for the transformation?

Because the job fits on one node and a distributed engine charges twice the rate to shuffle data that never needed moving. Measured: 0.856 CU-hours on the Python kernel against 1.712 modelled for the same executing time on the starter pool. The model is deliberately generous, assuming Spark matches DuckDB's wall time when in practice it is usually slower on a job this size. Above a single node's memory, that argument reverses and Spark wins.

Why not a Warehouse?

Not because of the rate: since August 2026 a Warehouse vCore costs 0.538 CU, close to a notebook's 0.5. Because of what gets billed. The notebook bills the 8 vCores it was given, only while it executes; a Warehouse bills every vNode it allocates, busy or waiting, and background work while it exists. A production pilot, anonymised, measured about 60 CU-s per Warehouse engine-second against 4, and about 9,800 CU-s against 260 to rebuild the same three tables. The honest trade runs the other way on raw speed and on V-Order, which warehouses write by default and which cost this pipeline a separate Spark step, at most 233 s and about eleven cents.

Why is the report written in JavaScript?

Because the page is the visual. A measure can carry roughly 2.1M characters, which is enough to ship both a pre-aggregated cube and a renderer, so one visual replaces a dozen and the layout stops being a negotiation with the canvas. The cost is that the measure is now code, which is why it is generated and bisected against Desktop rather than hand-edited.

Why keep a known defect in the mirror?

One row deleted before the slot existed cannot be removed through the slot; only a re-seed clears it. Hiding it would have been a line of code. Instead the acceptance pass measures the difference on every run and names the row, because a pipeline that quietly rounds away a one-row discrepancy will quietly round away a larger one later.
