# 50 million rows, on-prem PostgreSQL to a Power BI report, on Microsoft Fabric

An end-to-end data platform built in the open: **50,000,001 rows of deliberately
filthy banking data** generated from scratch, landed in on-premises PostgreSQL,
mirrored into OneLake through **open mirroring with live CDC**, transformed by
**DuckDB running on a Fabric Python notebook**, served as a **Direct Lake**
semantic model, and consumed by a Power BI report that writes analyst decisions
back into the lake.

Every number below was measured on the running system, not estimated. The
complete record of how it was built, including every mistake and what it cost,
is in [BUILD_LOG.md](BUILD_LOG.md). The acceptance pass that proves the current
state is in [UAT.md](UAT.md), regenerated by `scripts/uat.py`.

## The short version

| | |
| --- | --- |
| Source | PostgreSQL 16 on `localhost`, one table, 100 columns, **every column TEXT**, 48 GB as loaded |
| Into OneLake | Open mirroring: 10.5 GB seed in 29 min, then continuous CDC from the write-ahead log |
| Transformation | DuckDB on a Fabric **Python** notebook, 8 vCores: **49,406,792** conformed rows in 12.8 min |
| Model | Direct Lake, 9 tables, 8 relationships, 17 measures, **no copy of the data** |
| Report | 4 pages, rendered by JavaScript shipped inside a DAX measure |
| Write-back | Analyst decisions land in a Fabric SQL database and appear in OneLake as Delta |
| Compute cost | **1.51 CU-hours** for a full rebuild, about **$0.27**, against 2.51 modelled for the Spark equivalent |
| Query latency | ~1 second warm for any page of the report, over the full 49.4M-row fact |

## What this demonstrates

| Phase | What happens | Layer |
| --- | --- | --- |
| **1** | On-prem PostgreSQL to OneLake via open mirroring: an initial seed plus continuous CDC read from the WAL through a logical replication slot | Bronze, raw, all TEXT |
| **2** | DuckDB on a Fabric Python notebook: cleaning, typing, conforming, seven measured risk rules, dedupe, star schema. Spark is used only for the V-Ordered Delta write | Silver to Gold |
| **3** | Direct Lake semantic model over the gold tables, reconciled to the source by DAX | Semantic |
| **4** | A four-page report, an operational SQL store, and user data functions that write analyst decisions back | Application |

Each phase is deliberately constrained so the next one has something honest to
do. The bronze layer is text-only and genuinely dirty, which is what makes the
Phase 2 cleaning work meaningful rather than decorative. The surrogate key added
for mirroring (`_mirror_row_id`) is also what makes the 593,209 exact duplicate
rows resolvable downstream, since no subset of the 100 business columns is
unique, and it is the join key the write-back layer uses to tie a decision to a
transaction.

## The pipeline

```
generate.py              50M x 100 messy TEXT columns          -> CSV on D:, 45 GB
load_postgres.py         parallel COPY, all TEXT, LOGGED       -> landing.raw_txn, 48 GB
                         + surrogate key _mirror_row_id
snapshot_to_fabric.py    DuckDB -> zstd parquet -> azcopy      -> mirror LandingZone
cdc_to_fabric.py         WAL -> logical slot -> parquet + __rowMarker__
                         Fabric applies insert / update / delete to the Delta table
01_build_gold.Notebook   DuckDB, Python kernel, 8 vCores, over a shortcut to the mirror
                         clean -> conform -> score -> dedupe -> star  -> gold parquet
02_vorder_write.Notebook Spark rewrites gold as V-Ordered Delta (DuckDB cannot)
03_verify.Notebook       counts, V-Order properties and orphan keys, written to evidence
build_semantic_model.py  Direct Lake TMDL, 17 measures, alerts priced in analyst headcount
build_report.py          the four-page PBIP, live on the model
fincrime_fn (udf/)       analyst decisions -> Fabric SQL -> OneLake Delta -> back to DuckDB
```

## The decisions worth arguing about

### Open mirroring, and why a seed plus CDC

Fabric's **native** database mirroring connects directly to the source, but it
supports Azure SQL Database, SQL Server, Cosmos DB, Oracle, SAP and **Azure
Database for PostgreSQL**. A PostgreSQL instance on `localhost` is not reachable
by Fabric and is not a supported native source, so **open mirroring** is the
correct mechanism: the publisher writes change files into a landing zone and
Fabric's replication engine applies them to Delta tables.

Mirroring is seed-then-stream. The seed establishes the baseline; CDC keeps it
live. A change feed with no seed would leave Fabric holding only rows that
changed after the slot was created, which is not a mirror and gives Phase 2
nothing to model.

**Create the replication slot before you take the snapshot.** This project did
it the other way round and paid for it: two rows fell into the gap between the
snapshot and the slot, one deleted at the source and one inserted, and because
the errors had opposite signs *the row counts still matched exactly*. Finding
them needed a distinct-key comparison and a per-bucket hash histogram.
BUILD_LOG section 40 has the full account, and `scripts/build_probe_mirror.py`
generates the probe that finds it.

### DuckDB on a Python notebook, not Spark

The transformation is a single-node job over 10.5 GB compressed. Spark's
starter pool bills a documented minimum of 8 CU; a Python notebook at 8 vCores
bills 4. Same work, half the rate, and no shuffle.

| Step | CU | Wall time | CU-hours | at $0.18/CU-h |
| --- | --- | --- | --- | --- |
| DuckDB transformation, Python 8 vCores | 4 | 895 s | 0.994 | $0.18 |
| V-Order write, Spark starter pool | 8 | 233 s | 0.518 | $0.09 |
| **This pipeline** | | | **1.512** | **$0.27** |
| Modelled: the same transformation on Spark | 8 | 895 s | 1.989 | $0.36 |
| **Alternative** | | | **2.507** | **$0.45** |

The transformation step costs **half**; the pipeline as a whole **40% less**.
The alternative is modelled, not measured, and the model is deliberately tilted
in its favour: it assumes Spark takes the *same* wall time, when a distributed
engine on a job that fits one node is usually slower. A Warehouse T-SQL path
would also copy all 49.4M rows into warehouse storage first, a second copy
Direct Lake never makes, and that copy is not priced here at all. The rate is
the one assumption, and `00_README.Notebook` recalculates the whole table live
from the jobs API so it can never go stale.

### Why Spark is still in the pipeline

DuckDB cannot write V-Order, writes Delta INSERT-only with no MERGE or schema
evolution, and never writes checkpoints, so a table written entirely by DuckDB
accumulates an unbounded transaction log. V-Order is what makes Direct Lake
fast. Splitting on exactly that boundary, DuckDB for the analytics and Spark
for the write, costs 233 seconds and keeps both engines doing what they are
good at.

### Direct Lake means one copy

The semantic model reads the same Delta files the notebook wrote. Nothing is
imported, nothing is refreshed on a schedule, and there is no second copy to
keep in sync. The first query after a reframe pays for transcoding the fact's
columns into memory (7 to 11 seconds); every query after that answers in about
a second over 49,406,792 rows.

### A report rendered by JavaScript inside a DAX measure

The four pages are not built from native visuals. Each page is a single HTML
Content visual fed by a DAX measure that ships both a pre-aggregated cube and
the JavaScript that renders it, with no CDN and no external dependency. The
overview page ships a 2,508-cell cube and uses about 4% of the roughly 2.1M
character ceiling a measure can hold. `scripts/build_report.py` generates the
whole PBIP, including a native page navigator so the report is usable outside
Desktop.

### The loop closes

A Fabric SQL database mirrors itself to OneLake as Delta **with no
configuration at all**. So an analyst verdict written through a user data
function into `fincrime_ops` becomes a Delta file that the next gold rebuild
can join back to `fact_alert` with `_mirror_row_id`. Alert precision stops
being simulated against a seeded label and starts being measured against what
analysts actually did. The UAT proves this hop by hop on every run.

### Where the data lives, and why not here

The CSV is roughly **45 GB** and the PostgreSQL table **48 GB** as loaded, now
50 GB after the update and delete probes left dead tuples behind. Both
live on `D:`, with the Postgres table on a `bigdata` tablespace at `D:/pgdata/banking_raw`
so the load does not fill the system drive. Only code lives in this repository,
which the `.gitignore` enforces.

## Reproducing it

### Generate the source data

```bash
python scripts/generate.py --rows 50000000 --chunk 1000000 --out D:/duckdb-fabric-data/csv
python scripts/validate.py --path D:/duckdb-fabric-data/csv
```

| flag | meaning |
| --- | --- |
| `--rows` | total rows, duplicates included. Lands on the number exactly. |
| `--chunk` | base rows per CSV file. 1M gives ~921 MB files. |
| `--dup-rate` | fraction re-emitted as exact duplicate rows (default 1.2%) |
| `--resume` | skip chunk files that already exist |
| `--seed` | reproducibility |
| `--threads`, `--memory-limit` | DuckDB tuning |

Measured on this machine (16 threads, 31 GB RAM): **~42,500 rows/s**, **921 MB
per million rows**. Chunk size matters: at 25k rows per chunk throughput
collapses to ~6,000 rows/s because compiling the very large 100-column SQL
statement dominates. Keep chunks at 1M.

### Load PostgreSQL

Put the password in libpq's password file so it never appears on a command line
or in shell history. On Windows that is `%APPDATA%\postgresql\pgpass.conf`:

```
localhost:5432:*:postgres:YOUR_PASSWORD
```

```bash
python scripts/load_postgres.py --path D:/duckdb-fabric-data/csv --jobs 6 --logged
```

**Pass `--logged`.** The default is UNLOGGED, which is faster to load but is
never captured by logical replication, so the mirror's CDC would silently see
nothing. Loading LOGGED also avoids rewriting a 48 GB table with
`ALTER TABLE ... SET LOGGED` later. Measured: 50,000,000 rows in 10.9 minutes at
76,465 rows/s with six connections. `--resume` skips files already recorded in
`landing._load_log`.

### Mirror, transform, model, report

**Order matters here.** Create the slot first, then snapshot. A slot created
after the snapshot cannot see anything that changed while the snapshot was
being taken, and those changes are lost with no error and no count mismatch to
warn you. This project learned that the expensive way; see the mirroring
section above.

```bash
python scripts/cdc_to_fabric.py --setup              # 1. create the slot FIRST
python scripts/snapshot_to_fabric.py                 # 2. then seed the mirror
python scripts/cdc_to_fabric.py --run --interval 10  # 3. stream changes, leave running

fab job run "fabric duckdb.Workspace/01_build_gold.Notebook"     # DuckDB on capacity
fab job run "fabric duckdb.Workspace/02_vorder_write.Notebook"   # V-Order
fab job run "fabric duckdb.Workspace/03_verify.Notebook"         # prove it

python scripts/build_semantic_model.py && fab import ...         # Direct Lake model
python scripts/build_report.py --open                            # the PBIP
python scripts/folderize_workspace.py                            # tidy the workspace
python scripts/uat.py                                            # prove all of it
```

### Entities stay coherent

Attributes that belong to an entity rather than to a transaction are chosen by
`hash(entity_id)`, not `random()`. A customer keeps the same underlying name,
date of birth, occupation and address across every one of their rows, and a
merchant keeps the same MCC.

The mess is applied *on top* of that, which produces the real problem worth
practising on: one customer appearing as `Ahmad bin Abdullah`,
`AHMAD BIN ABDULLAH`, ` ahmad  bin abdullah ` and `Abdullah, Ahmad`, rather
than the useless alternative where every row is a different person and no join
or dedupe exercise means anything.

### The mess catalogue

Measured on a 300k-row sample:

* **mean 18.4%** of values per column are null, null-like or whitespace-padded
* null lookalikes: `NULL`, `N/A`, `NA`, `-`, `unknown`, `none`, `#N/A`, `''`
* **five date formats** in one column: `2024-03-05`, `05/03/2024`, `03/05/2024`,
  `5-Mar-24`, `05.03.2024`
* sentinel dates: `1900-01-01`, `9999-12-31`, `0000-00-00`, `1970-01-01`
* money as text: `1,234.50`, `RM99.00`, `(45.00)` for negatives, bare floats
* timestamps with, without and half-with timezone, plus raw epoch integers
* leading-zero loss and float artefacts in `account_no` and `card_last4`
* **1.18% exact duplicate rows**, and 31 spellings of Malaysia, 34 of
  `txn_type`, 43 of `card_brand`
* free text containing commas and quotes, correctly CSV-quoted

Which produces, on that sample: `posting_date` parses cleanly 52.4% of the
time, `txn_amount` 81.7%, `balance_after` 70.5%, `txn_datetime` 95.8%.

## What came out the other end

| | |
| --- | --- |
| Transactions | **49,406,792** (50,000,001 source rows less 593,209 exact duplicates) |
| Rule firings | 65,175,479 across seven rules |
| Alerts raised | 1,423,088, a **2.88%** alert rate |
| Orphan dimension keys | **0**, across every dimension |
| Distinct customers | 5,112,692 |
| Total amount | 17,808,657,535.30 |

The seven risk rules are measured, not invented: each was calibrated against
its real fire rate on the full population. That distinction matters. Three of
them depend on a window over a customer's history, and their fire rates moved
by up to 25x between a 2M-row sample and the full 50M, because history depth is
a function of how much of the population is in the sample. **Any rule whose
definition references a window over an entity must be calibrated on the full
population, not a slice.**

## Notes and gotchas

The ones that cost real time. [BUILD_LOG.md](BUILD_LOG.md) has the rest, with
the evidence.

* **A DuckDB session's timezone can change your results.** `to_timestamp()`
  returns `TIMESTAMPTZ` and coerces the whole expression, so every hour and
  date derived from an epoch string depended on where the code ran. The laptop
  (Asia/Dhaka) and the capacity (UTC) disagreed by six hours on exactly those
  rows. Use `make_timestamp()` and pin `SET TimeZone='UTC'`.
* **Ties in a window function are not stable.** A `row_number() OVER (... ORDER BY ts)`
  over exact duplicates broke arbitrarily, so roughly half of 160,000 firings
  landed on the copy that dedup then dropped. The tiebreak must agree with the
  dedup rule.
* **Naive timestamps break the Spark handoff.** DuckDB writes them with
  `isAdjustedToUTC=false`; Spark reads that as `TIMESTAMP_NTZ`, which the Delta
  tables and Direct Lake do not accept. Export instants.
* **Fabric parses the UDF decorator statically.** `alias=ALIAS` is read as the
  literal string `"ALIAS"`. The alias must be a string literal in every
  decorator.
* **`%%configure` must be the first cell** of a notebook, and building it with
  `%`-formatting silently turns `%%` into `%`, a line magic that does not
  exist. The generators validate this before writing.
* **A Python-kernel notebook needs `kernel_info.name = jupyter`** and
  `language_group = jupyter_python` in its metadata, or it lands on Spark and
  every cost figure is wrong by a factor of two.
* `strftime` in DuckDB requires a **constant** format string, so mixed date
  formats are built with `CASE`, not by indexing a list.
* Print through `PYTHONIOENCODING=utf-8` on Windows; cp1252 cannot render
  DuckDB's box-drawing output.
* Generating into a temp table before writing is what makes *exact* duplicates
  possible; a re-scan would re-roll `random()` and produce near-duplicates.

## Status and limits

* Fabric **Apps** (`AppBackend`) are region-gated. The trial capacity here is
  UK South, where the item type returns `403 FeatureNotAvailable`. The
  application layer is therefore a Power BI report plus user data functions,
  which is why `FABRIC_APP_PLAN.md` exists and stops where it does.
* The mirror carries **one extra row** against the source: a row deleted before
  the replication slot existed, which cannot be removed through the slot and
  needs a re-seed. It is documented, measured on every UAT run, and is the
  reason the "slot before snapshot" rule is stated above in bold.
* The cost comparison's **rate** is an assumption; the CU-hours are measured.
* The data is synthetic. No real customer data was used, generated or implied.
